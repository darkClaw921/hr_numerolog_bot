# Архитектура проекта

Telegram-бот нумеролог (aiogram 3, Python 3.12, менеджер uv). Считает матрицу
Пифагора по дате рождения, даёт интерпретации секторов и качеств, поддерживает
личный кабинет (сохранение людей, история поисков) и платные функции по подписке.

БД (SQLite) спроектирована как **общее хранилище**: в будущем отдельный бот
совместимости будет читать те же профили людей (таблица `people`) из того же файла.

## Ключевые компоненты

### Слой БД (`src/db/`)
SQLAlchemy 2.0 (async) + aiosqlite. Один файл SQLite, режим **WAL** и
`foreign_keys=ON` (включаются на каждом соединении в `session.py`). Схема
создаётся при старте через `init_models()` (`Base.metadata.create_all`).

Таблицы:
- **bot_users** — пользователи Telegram (ключ `telegram_id`), общие для обоих ботов.
- **people** — главная сущность: `birth_date` (источник истины), опциональные
  `display_name`/`full_name`, `calc_snapshot` (JSON-кэш расчёта), `calc_version`,
  `destiny_number` (отдельной колонкой для SQL-фильтрации). На неё ссылается бот совместимости.
- **search_history** — история поисков пользователя.
- **subscriptions** — статус подписки (`is_premium`, `expires_at`); включается вручную.
- **compatibility_results** — задел под бот совместимости (текущий бот не пишет).
- **referrals** — кто кого пригласил и выдан ли бонус (`rewarded_at`, `bonus_days`).

Доступ к данным — только через репозитории (`repositories.py`). Middleware
открывает сессию на апдейт, прокидывает репозитории в данные хендлеров,
коммитит при успехе/откатывает при ошибке и регистрирует пользователя.

### Расчёты (`src/utils/numerology.py`)
`calculate_all(date_str)` — детерминированная функция от даты `DD.MM.YYYY`.
`validate_results()` проверяет полноту коэффициентов/матрицы/ЧС перед показом.
`CALC_VERSION` хранится со снапшотом, чтобы бот совместимости мог распознать
устаревший кэш. `format_date_for_calc(date)` форматирует дату из БД с ведущими нулями.

### Форматирование (`src/formatting.py`)
Блоки результата (`_matrix_block`, `_coefficients_block`, `_destiny_block`,
`_additional_numbers_block`) переиспользуются и в базовом экране, и в полном отчёте.
По ТЗ блок «Дополнительные числа» перемещён вниз. `build_full_report()` собирает
единый HTML; `build_full_report_markdown()` — чистый Markdown (через `_html_to_markdown`)
для файла `.md`. Длинные сообщения режутся `send_long_message()`.

### Gating платных функций (`src/access.py`)
`is_premium_feature(key)` — платные: полный отчёт, комбинации и коэффициенты-качества
(БЫТ, Темперамент, Семья, Стабильность; скрытая Трансформация). Бесплатны: секторы 1-9,
Целеустремлённость, Число Судьбы. `is_premium(user_id, repo)` — проверка статуса
(сначала `PREMIUM_USER_IDS`, затем БД). `require_premium(event, feature, repo)` —
показывает paywall, если доступа нет. Платные кнопки помечаются 🔒 в клавиатуре.

### Хендлеры (`src/handlers/`)
Навигация по кнопкам не использует in-memory кэш: дата рождения зашита в
`callback_data` (формат `тип:...:дата`), результат пересчитывается из даты —
работает и после рестарта. Личный кабинет добавляет людей через FSM
(`AddPerson`: дата → имя → ФИО, имя/ФИО опциональны с кнопкой «Пропустить»).
Открытие сохранённого человека показывает тот же экран результатов в режиме профиля:
к `callback_data` добавляется суффикс `:<person_id>`, и «Назад» из секторов, качеств,
комбинаций и отчёта возвращает в профиль; в профиле — «Назад к людям» и «Личный кабинет»,
кнопки «Сохранить» нет (она скрыта и при вводе уже сохранённой даты). Навигация
редактирует сообщение на месте (`edit_or_send`).

## Алгоритм расчётов

1. **Первое доп. число**: сумма всех цифр даты (18.08.1984 → 39).
2. **Второе доп. число**: сумма цифр первого (39 → 12).
3. **Третье доп. число**: первое − (2 × первая значащая цифра дня) (39 − 2×1 = 37).
4. **Четвёртое доп. число**: сумма цифр третьего (37 → 10).
5. **Матрица**: цифры даты и доп. чисел распределяются по секторам 1-9.
6. **Коэффициенты**: Темперамент (3/5/7), Быт (4/5/6), Цель (1/4/7), Семья (2/5/8),
   Привычки/Стабильность (3/6/9, с `CALC_VERSION = 2`).
7. **Число Судьбы**: сумма цифр даты до однозначного (11 — мастер-число).

## Зависимости

- **aiogram** ≥ 3.24 — Telegram Bot API (async).
- **python-dotenv** — переменные окружения.
- **SQLAlchemy[asyncio]** ≥ 2.0 — ORM/схема как код.
- **aiosqlite** — async-драйвер SQLite.
- **aiohttp** — HTTP-клиент aiogram и сервер вебхука Prodamus.

## Платежи Prodamus (`src/payments/`)

Рекуррентная подписка через клубную систему Prodamus. Премиум включается только
уведомлением (`urlNotification`) с валидной подписью — возврат пользователя на
страницу успеха ничего не активирует.

- `hmac_sign.py` — подпись, совместимая с PHP `Hmac::create`: значения к строкам,
  рекурсивный `ksort`, `json_encode` без пробелов с экранированием `/`, HMAC-SHA256.
- `formdata.py` — разбор тела уведомления в PHP-подобную структуру. Подпись
  проверяется ПОСЛЕ разбора: Prodamus подписывает исходный массив, form-urlencoded —
  только транспорт. Массив с ключами `0..n-1` должен стать списком, иначе подпись
  не сойдётся.
- `prodamus.py` — сборка подписанной ссылки на оплату и REST-метод `setActivity`
  (отмена автопродления).
- `service.py` — применение события к БД: продление, отмена, неуспешное списание.
- `webhook.py` — aiohttp-приложение, поднимается в `src.bot.main()` через
  `AppRunner` рядом с long polling (при `PAYMENTS_ENABLED`).

Ключевые инварианты:

- **Идемпотентность.** `payments.event_key` уникален; повторная доставка того же
  уведомления возвращает 200 и ничего не меняет.
- **Только свои order_id.** Уведомление сопоставляется с пользователем через
  `payment_intents` (order_id, выданный ботом), затем через `customer_extra`,
  телефон и email — подделать идентификатор заказа нельзя.
- **Продление от конца периода.** `expires_at` = `date_next_payment` + запас
  (`PRODAMUS_GRACE_DAYS`), иначе `max(expires_at, now) + SUBSCRIPTION_PERIOD_DAYS` —
  досрочное списание не съедает остаток.
- **Отмена не снимает доступ.** `prodamus_active=False` и `cancelled_at`, а
  `is_premium`/`expires_at` не трогаются: оплаченный период дорабатывает, дальше
  доступ снимает сам `is_active()`. Отдельный крон не нужен.
- **Схема аддитивна.** Новые колонки nullable, миграции — `src/db/migrations.py`
  (alembic в проекте нет), БД остаётся совместимой с ботом совместимости.
